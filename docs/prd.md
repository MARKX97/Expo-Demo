# 电梯故障派工与交接 App

## 1. 产品目标

为单个物业项目的电梯区域主管和电梯工程师提供移动端故障派工闭环，减少电话、聊天记录和重复确认带来的沟通成本。

本产品只记录和追踪工单。困人、停梯等紧急事件仍必须遵循既有线下应急流程，不能以本应用替代应急处置。

## 2. 范围与非目标

### V1 包含

- 已创建账号的邮箱密码登录和忘记密码。
- 主管创建、查看、改派未处理工单。
- 工程师查看分配给自己的工单、开始处理、填写结果并关闭。
- 云端保存工单与 1–3 张现场照片。

### V1 不包含

- 自助注册、App 内账号管理、组织或项目切换。
- 推送通知、评论、工单删除、已开始工单的改派。
- 紧急救援流程、设备台账、统计报表和离线编辑。

## 3. 角色与权限

| 角色 | 权限 |
| --- | --- |
| 电梯区域主管 (`elevator_supervisor`) | 创建工单；查看项目全部工单；将 `assigned` 工单改派给已启用工程师。 |
| 电梯工程师 (`elevator_engineer`) | 仅查看分配给自己的工单；将工单开始处理或关闭。 |

账号由项目管理员在 Supabase 控制台预创建，并在用户资料中配置角色和启用状态。App 不提供注册入口。

## 4. 登录与账号

- 登录方式：邮箱 + 密码。
- 登录页提供“忘记密码”；系统向已存在的邮箱发送密码重置链接，并回到 App 完成重设。
- 密码重置使用 PKCE；邮件链接必须在发起重置的同一设备打开，失败时可在当前设备重新发送。
- 未登录用户不能读取照片、人员或工单数据。
- 停用账号不能登录或操作数据。

## 5. 工单模型

```ts
type UserRole = 'elevator_supervisor' | 'elevator_engineer';
type WorkOrderStatus = 'assigned' | 'in_progress' | 'closed';
type WorkOrderPriority = 'normal' | 'urgent';
```

主管创建工单时必须填写：

- 电梯区域（自由文本）
- 梯号或设备编号（自由文本）
- 故障描述
- 优先级：一般或紧急
- 接手工程师
- 1–3 张现场照片

工单记录还保存创建人、接手人、创建时间、状态更新时间、关闭时间和处理结果。关闭时必须填写处理结果；关闭后的工单只读，不支持编辑或删除。

## 6. 状态机与核心流程

```text
主管创建并指派 ──> assigned ──工程师开始处理──> in_progress
                                                │
                                      工程师填写结果并关闭
                                                │
                                                v
                                             closed
```

1. 主管选择已启用工程师，提交成功后工单状态为 `assigned`。
2. 工程师在“我的工单”中看到被分配的工单，并可将其更新为 `in_progress`。
3. 工程师填写非空处理结果后，才能将工单更新为 `closed`。
4. 主管只能改派仍为 `assigned` 的工单；一旦工程师开始处理，不允许改派，避免责任归属不清。
5. 紧急工单在列表置顶并使用醒目标识，但不自动通知或触发外部应急流程。

## 7. 数据与失败处理

- Supabase Auth 负责认证；数据库保存用户资料和工单；Storage 保存现场照片。
- Row Level Security：主管可读全量工单并创建/改派待处理工单；工程师仅可读写分配给自己的工单。工程师只可执行允许的状态流转。
- 创建工单前必须成功上传全部照片。任一上传失败时，不创建工单；用户可重试或取消。
  App 仍可通信的失败/取消路径必须清理已上传临时文件；强制终止或断电不属于 V1
  自动清理保证，开发期由管理员清理孤儿对象。
- 提交、状态变更和改派期间禁用重复点击。服务器拒绝的并发更新应提示失败并重新加载工单详情。
- 列表下拉刷新与页面重新聚焦时从云端加载最新数据；V1 不使用实时订阅或推送。

## 8. 页面

- 登录 / 忘记密码 / 重设密码
- 主管工单总览：全部工单、状态与紧急标记
- 新建工单：填写字段、选择工程师、上传照片
- 工程师“我的工单”：`assigned` 和 `in_progress` 工单
- 工单详情：状态、照片、信息、开始处理、关闭或待处理改派
- 个人中心：当前用户与退出登录

## 9. 验收标准

- `AC-AUTH-01`：主管和工程师能用预创建的邮箱密码账号登录。
- `AC-AUTH-02`：工程师能在发起重置的同一设备收到并打开密码重置邮件，通过 App 深链设置
  新密码后登录。
- `AC-WO-01`：主管可创建含 1–3 张照片的工单，并只能选择已启用工程师。
- `AC-WO-02`：被指派工程师在另一会话刷新后可看到工单，开始处理并填写结果关闭。
- `AC-PERM-01`：主管可查看全部工单，并仅能改派 `assigned` 状态的工单。
- `AC-PERM-02`：工程师不能查看、更新或改派其他工程师的工单。
- `AC-FAIL-01`：空处理结果和重复提交均被阻止，且不产生额外工单或状态写入。
- `AC-UPLOAD-01`：在 App 仍可执行补偿的照片上传失败、工单创建失败或用户取消路径下，
  可以重试/取消，且 Storage 不保留本次提交的孤儿对象。
- `AC-CONCURRENCY-01`：版本冲突不会覆盖云端新数据，客户端重新加载并提示用户重试。
- `AC-DELIVERY-01`：Android 与 iOS 测试构建可安装、启动并完成登录 smoke flow。

自动测试、E2E 和最终证据映射见 [测试与质量策略](TESTING.md)。

## 10. 技术与交付约束

- 使用单一 Git 仓库保存移动端、Supabase、文档和交付记录；V1 只计划一个 JavaScript 应用，不额外引入 workspace 编排工具。
- 移动端使用 Expo + TypeScript，不使用 Expo Go。
- Android 使用 EAS 生成可直接安装的 APK；iOS 使用 EAS Ad Hoc IPA，或在没有付费 Apple Developer 账号时使用 macOS + Xcode 本地签名。
- PoC 不需要上架应用商店，但必须在至少一台 Android 或 iOS 开发设备上运行。
- 账号开通与登录数据必须真实落入 Supabase Auth/Postgres，不使用纯 mock 替代后端。
- 仓库必须包含环境准备与快速开始说明 `README.md`、产品定义 `docs/prd.md`，以及脱敏后的完整用户可见 AI 开发对话 `docs/ai-chat-history.jsonl`。
